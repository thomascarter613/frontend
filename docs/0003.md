Using the professional maximum-workspace application, production design system, and interaction architecture already created, now perform a **Product Architecture and View Taxonomy pass**.

Do **not** redesign the application shell.

Do **not** create a second unrelated design system.

Do **not** replace the interaction model.

Do **not** turn the product into a collection of disconnected dashboard pages.

Instead, define and design the **complete family of product surfaces that can inhabit the existing workspace shell**.

The first three passes established:

1. the application shell and visual architecture
2. the component/design system
3. the interaction and workspace behavior model

This fourth pass must answer:

> **What kinds of work can actually occur inside this environment, and what canonical UI surface should be used for each kind of work?**

The application remains intentionally **domain-neutral and general-purpose**.

It should be capable of supporting:

- project management
- knowledge management
- research
- documents
- structured data
- task management
- planning
- administration
- analytics
- automation
- content management
- software/technical work
- operational workflows
- collaboration
- asset management
- reporting

without becoming visually or structurally fragmented.

The goal is to establish a coherent **product-surface architecture** comparable in breadth to a mature professional application platform.

The output should be a **systematic catalog of reusable view archetypes**, not hundreds of unrelated screenshots.

---

# 1. CORE PRODUCT ARCHITECTURE PRINCIPLE

Treat the application as:

```text
Application Platform
│
├── Persistent Workspace Shell
│
├── Product Modules
│
├── Resource Types
│
├── View Types
│
├── Tool Surfaces
│
└── Contextual Inspectors
```

These concepts must remain distinct.

# 2. DEFINE THE TERMINOLOGY

Use the following terminology consistently throughout the file.

## Application Shell

The persistent frame surrounding the user's work.

Includes:

```text
Global Bar
Activity Rail
Primary Sidebar
Workspace Header
Breadcrumb / Context Bar
Editor Groups
Inspector
Bottom Panel
Status Bar
Overlay Layer
```

## Module

A major functional area of the application.

Examples:

```text
Projects
Documents
Tasks
Data
Analytics
Automations
```

## Resource

A persistent object the user can create, open, inspect, link, move, share, or modify.

Examples:

```text
Project
Document
Task
Dataset
Record
Dashboard
Workflow
File
```

## View

A particular representation of resources.

Examples:

```text
Table
Board
Calendar
Timeline
List
Graph
```

A view is **not necessarily a different resource**.

The same underlying tasks might appear in:

```text
Table View
Board View
Calendar View
Timeline View
```

## Tool Surface

A temporary or auxiliary working surface.

Examples:

```text
Search
Terminal
Activity
Logs
Command Palette
Preview
Compare
```

## Inspector

Contextual information and controls for the currently selected resource or element.

Do not confuse these concepts.

---

# 3. ARCHITECTURAL RULE

A resource may support multiple representations.

For example:

```text
Task Collection
│
├── List View
├── Table View
├── Board View
├── Calendar View
└── Timeline View
```

Do not create completely separate product architectures for each representation.

The view changes.

The underlying resource remains the same.
