Using the complete workstation architecture established through **Passes 1–9**, now perform a **Frontend Engineering Contract, Implementation Architecture, Component API, State Management, Testing, and Developer Handoff pass**.

Do **not** redesign the interface.

Do **not** invent a second design system.

Do **not** flatten the workstation into a collection of disconnected React pages.

Do **not** treat developer handoff as merely adding redlines, spacing annotations, or CSS values.

Instead, transform the system into an **implementation-ready architectural specification** from which a professional frontend engineering team could build the application without having to reverse-engineer design intent.

# 481. FINAL ENGINEERING DOCTRINE

End the page with the following architectural doctrine:

```text
1. File defines the design contract; code implements it.

2. Tokens encode design decisions.

3. Primitives encode layout mechanics.

4. Components encode reusable semantics.

5. Patterns encode recurring workflows.

6. The Workspace Shell owns geometry, not business data.

7. Resource identity must remain stable across rename, move, and View changes.

8. Views are representations of Resources, not separate Resources unless the domain requires it.

9. Commands represent user intent independently of where the user invokes them.

10. Menus, toolbars, keyboard shortcuts, and the Command Palette should reuse Commands.

11. Focus, selection, active state, and hover are different concepts.

12. Server state, workspace state, form state, and ephemeral UI state should remain distinct.

13. Editor layout is a recursive split structure, not a fixed two-pane layout.

14. Docking and editor splitting are separate systems.

15. Major workspace state should be serializable and recoverable.

16. Permissions should be expressed through capabilities, not hard-coded role assumptions.

17. Extensions contribute through stable registries and bounded extension points.

18. Optional systems must fail independently.

19. Long-running work belongs in Jobs.

20. Large data must support virtualization or progressive loading.

21. Responsive behavior should preserve workstation semantics rather than converting the product into a generic mobile stack.

22. Accessibility behavior is part of every component contract.

23. Keyboard behavior is a first-class implementation requirement.

24. Components should expose semantic APIs rather than implementation styling knobs.

25. Composition should be preferred over variant explosion.

26. Feature modules may depend on platform infrastructure; platform infrastructure must not depend on feature modules.

27. Persistent shell components should not remount for ordinary Resource changes.

28. User-entered work should survive recoverable failure.

29. Testing must verify behavior, accessibility, visual consistency, resilience, and performance.

30. The architecture should make the eleventh feature module easier to add than the first.
```
