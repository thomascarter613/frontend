Using the professional workspace shell, production design system, interaction architecture, and product-surface taxonomy already established, now perform a **Canonical Resource/Object Model and Information Architecture pass**.

Do **not** redesign the application shell.

Do **not** create additional arbitrary modules merely to make the product appear larger.

Do **not** treat every screen as an independent page with its own unrelated data model.

Do **not** invent separate object concepts when an existing canonical resource type can represent the same thing.

The first four passes established:

1. the persistent workspace shell and visual architecture
2. the production component/design system
3. the interaction and workspace behavior model
4. the product modules, surfaces, and view archetypes

This fifth pass must answer:

> **What are the canonical things that exist inside this application, how are they identified, organized, related, represented, addressed, discovered, and manipulated?**

The goal is to establish a coherent **resource/object model and information architecture** beneath the UI.

The application should now have a clear semantic structure rather than merely a collection of attractive screens.

The output should make it possible for:

- product designers
- information architects
- frontend engineers
- backend engineers
- database designers
- search engineers
- permissions engineers
- extension developers

to agree on what the major objects in the system actually are.

The priorities for this pass are:

**identity → containment → hierarchy → relationships → metadata → resource types → views → addressing → lifecycle → search → cross-linking → consistency**

# 2. DEFINE THE FUNDAMENTAL DISTINCTIONS

Use the following concepts consistently.

## Resource

A persistent identifiable object the user can:

```text
create
open
inspect
link
favorite
share
move
archive
search
reference
```

Examples:

```text
Project
Task
Document
Record
Dashboard
Workflow
File
```

## Container

An object whose primary purpose is organizing other objects.

Examples:

```text
Workspace
Folder
Space
Collection
```

Some resource types may also function as containers.

For example:

```text
Project
```

may contain:

```text
Tasks
Documents
Data
Files
```

## View

A saved representation or query over resources.

Examples:

```text
Table View
Board View
Calendar View
Timeline View
Filtered Task View
```

A View is **not the underlying data itself**.

## Relation

A typed connection between resources.

Examples:

```text
belongs to
parent of
child of
depends on
blocks
references
assigned to
owned by
related to
generated by
```

## Property

Structured metadata attached to a resource.

Examples:

```text
Status
Owner
Priority
Created
Updated
Tags
Due Date
```

## Content

The substantive body of a resource.

Examples:

```text
Document body
Task description
Workflow graph
Dashboard layout
File binary
Record field values
```

Keep these concepts distinct throughout the design.

At minimum, conceptually define:

```text

Resource Type
Title / Display Name
```

The system should nevertheless behave as though each resource has stable identity independent of where it appears.

# 4. IDENTITY VS LOCATION

A resource's **identity must not depend on its current folder or navigation location**.

For example:

```text
Architecture Specification
```

should remain the same resource if moved from:

```text
Projects / Platform Redesign / Documents
```

to:

```text
Knowledge / Architecture
```

Do not model moving a resource as destroying it and creating a new one.

This principle is essential for:

- links
- references
- history
- comments
- search
- favorites
- permissions
- activity
- open tabs

# 7. RESOURCE TYPES SHOULD NOT PROLIFERATE WITHOUT NEED

Before adding a new canonical type, ask:

> Is this truly a different kind of object?

or:

> Is this simply a different view, template, state, or subtype of an existing object?

Examples:

Do not automatically create separate canonical resource types for:

```text
Bug
Feature
Request
Issue
Action Item
```

if all can reasonably be represented as:

```text
Task
```

with:

```text
Type = Bug
Type = Feature
Type = Request
```

Similarly, do not necessarily create separate resource types for:

```text
Meeting Notes
Research Notes
Architecture Notes
```

when:

```text
Document
```

plus templates/properties can represent them.

# 205. FINAL PRINCIPLE

The product must not behave as though every screen owns its own copy of information.

The canonical mental model is:

```text
ONE RESOURCE GRAPH
+
MULTIPLE HIERARCHICAL CONTEXTS
+
MULTIPLE SAVED VIEWS
+
MULTIPLE WORKSPACE REPRESENTATIONS
```

A resource may appear:

```text
in a tree
in a table
on a board
in search
in a relation
in favorites
in activity
in a dashboard
in a split editor
```

without becoming multiple objects.

The UI is a collection of **representations of canonical resources**, not a collection of disconnected pages.
