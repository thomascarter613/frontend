Using the professional workspace shell, production design system, interaction architecture, product-surface taxonomy, and canonical resource/object model already established, now perform an **End-to-End Workflow and Task Architecture pass**.

Do **not** redesign the application shell.

Do **not** invent a new object model.

Do **not** create isolated “happy-path” demo screens that ignore the rest of the product.

Do **not** treat workflows as merely sequences of pages.

Instead, define how users accomplish meaningful goals **across resources, views, modules, panes, inspectors, commands, notifications, and lifecycle states**.

The first five passes established:

1. the persistent workspace shell and visual architecture
2. the production component/design system
3. the interaction and workspace behavior model
4. the product modules, surfaces, and view archetypes
5. the canonical resource/object model and information architecture

This sixth pass must answer:

> **How does a person actually use this system to accomplish work from beginning to end?**

The goal is to establish a rigorous **workflow architecture, task architecture, journey model, and cross-module operating model** for the entire workstation.

The application should no longer merely define:

- what exists
- what it looks like
- where it appears
- how individual controls behave

It must now demonstrate:

- how work enters the system
- how users triage it
- how resources are created
- how work is planned
- how people execute tasks
- how information is researched
- how resources are reviewed
- how decisions are made
- how work is approved
- how outputs are published or delivered
- how structured data is analyzed
- how automations are created and monitored
- how errors and interruptions are handled
- how work is resumed later
- how completed work becomes institutional knowledge

The priorities for this pass are:

**intent → entry point → orientation → capture → triage → planning → execution → context switching → collaboration → review → decision → completion → delivery → follow-up → recovery → continuity**

# 1. CORE WORKFLOW PRINCIPLE

Treat the application as a persistent operating environment in which user goals move through a sequence of **meaningful states**, rather than through a sequence of unrelated pages.

Conceptually:

```text
Intent
↓
Entry
↓
Capture
↓
Organize
↓
Plan
↓
Execute
↓
Review
↓
Decide
↓
Complete
↓
Publish / Deliver
↓
Monitor / Follow Up
↓
Archive / Learn
```

Not every workflow requires every stage.

The architecture should support shorter and longer variants.

---

# 2. DEFINE WORKFLOW TERMINOLOGY

Use these terms consistently.

## User Goal

The outcome a person is trying to achieve.

Example:

```text
Prepare and approve a technical architecture specification.
```

## Workflow

The end-to-end sequence through which the user reaches that outcome.

## Task

A discrete unit of work inside a workflow.

## Action

A single user operation.

Example:

```text
Change Status to Review
```

## State

The meaningful condition of a resource or workflow.

Example:

```text
Draft
In Progress
Review
Approved
Complete
```

## Transition

Movement from one state to another.

## Trigger

An event that begins or advances a workflow.

## Decision Point

A moment at which alternate paths are possible.

## Exception Path

A path caused by failure, rejection, missing information, conflict, or other deviation from the normal flow.

## Completion Condition

The condition proving the user's goal has been achieved.

---

# 3. WORKFLOW IS NOT THE SAME AS AUTOMATION

Maintain a strong distinction between:

```text
User Workflow
```

and:

```text
Automation Workflow
```

A User Workflow describes how people accomplish work.

An Automation Workflow is a canonical Workflow resource created in the Automations module.

Example:

```text
User Workflow:
Review and publish weekly project status.

Automation Resource:
Generate draft weekly status report every Friday.
```

The automation may support the user workflow but does not replace the conceptual distinction.

# 4. TASK HIERARCHY

Model user work at several levels.

```text
Outcome
└── Workflow
    ├── Stage
    │   ├── Task
    │   │   ├── Action
    │   │   └── Action
    │   └── Task
    └── Stage
```

Example:

```text
Outcome:
Launch Platform Redesign

Workflow:
Project Delivery

Stage:
Planning

Task:
Define milestones

Actions:
Create milestone
Set target date
Assign owner
```
