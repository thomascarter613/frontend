Using the complete workstation architecture already established through Passes 1–8, now perform a **Production Hardening, Resilience, Failure Modes, Concurrency, Offline, Recovery, Performance, and Edge-Case Architecture pass**.

Do **not** redesign the application.

Do **not** add decorative “error pages” as substitutes for actual resilience architecture.

Do **not** treat reliability as a collection of generic empty/error/loading states.

Do **not** assume every operation is instantaneous, every network request succeeds, every user has perfect connectivity, every Resource remains unchanged while open, every Extension behaves correctly, every background job completes, or every data set fits comfortably on screen.

Instead, systematically design how the workstation behaves when reality becomes difficult.

The first eight passes established:

1. persistent workspace shell and visual architecture
2. production design system
3. interaction and workspace behavior
4. product modules and surface taxonomy
5. canonical Resource/object model
6. end-to-end workflow/task architecture
7. collaboration, permissions, governance, security, and administration
8. extensibility, customization, integrations, and platform configuration

This ninth pass must answer:

> **What happens when operations are slow, interrupted, concurrent, partially successful, stale, unavailable, conflicted, disconnected, degraded, overloaded, incompatible, or recoverable?**

The goal is to evolve the system from:

```text
A sophisticated application that works under ideal conditions
```

into:

```text
A professional workstation that remains understandable,
recoverable, and trustworthy under real production conditions
```

Primary priorities:

**failure containment → state clarity → data preservation → concurrency → conflict resolution → optimistic updates → retries → background work → offline behavior → synchronization → stale data → partial success → recovery → undo → autosave → session restoration → performance → large datasets → virtualization → degraded mode → diagnostics → observability → edge cases → production acceptance testing**

```text

# 6. STATE TERMINOLOGY

Use consistent terms:

## Pending

Operation has been requested but has not started or completed.

## Running

Operation is actively executing.

## Queued

Operation is waiting behind other work.

## Success

Operation completed as intended.

## Partial Success

Some requested work completed, but some did not.

## Failed

Operation could not complete.

## Cancelled

User or system intentionally stopped the operation.

## Interrupted

Operation stopped unexpectedly and may require recovery.

## Retrying

System is attempting the operation again.

## Paused

Operation is intentionally suspended and may resume.

8. Make manual recovery obvious when automatic recovery ends.
9. Merge non-conflicting concurrent changes automatically.
10. Surface meaningful conflicts explicitly.
11. Offline work must clearly distinguish local from synced state.
12. Partial success is not full success.
13. Broken Extensions must not break core Resources.
14. Broken Integrations must not blank native content.
15. Historical state should be recoverable where practical.
16. Destructive operations require proportional safeguards.
17. Large data must not freeze the application.
18. Persistent failures belong in persistent diagnostic surfaces.
19. Safe Mode protects the platform kernel.
20. The user should always know what to do next.
```

# 639. FINAL RELIABILITY QUALITY BAR

The system should be able to answer clearly:

> What happens if saving fails?

> Is my work still there?

> What happens if I go offline?

> Which actions can continue offline?

> How do pending changes sync?

> What happens when two people edit the same field?

> What happens when two people edit different fields?

> What happens if a Resource is deleted while I am editing it?

> What happens if my permission changes while I am editing?

> What happens when my session expires?

> What happens when an Extension crashes?

> What happens when an Integration is unavailable?

> What happens if a Workflow partially succeeds?

> Can I retry only the failed portion?

> Can long operations run in the background?

> Where do I find failed operations later?

> Can I cancel an operation?

> Can interrupted work resume?

> What happens if the application closes unexpectedly?

> Are unsaved drafts recoverable?

> Can I restore an older version?

> What happens if a View references a deleted Field?

> What happens if schema migration only partially succeeds?

> What happens if external data is stale?

> How can I tell whether data is fresh?

> What happens with 100,000 rows?

> What happens with 100 open tabs?

> What happens if a search provider times out?

> What happens if only one Dashboard widget fails?

> Can the core application remain usable while optional systems are degraded?

> Is there a Safe Mode?

> Is there a Diagnostics center?

> Can a user recover without understanding backend architecture?
