Using the complex web application workspace UI already created in file 0000.md, **do not redesign the product from scratch**.

Instead, treat the existing visual design as the approved reference implementation and now **refactor it into a rigorous, scalable, production-grade design system and component architecture**.

The goal of this pass is to transform the current workspace from a collection of screens into a system that could realistically support a large application maintained by a professional product-design and frontend-engineering team.

Preserve the existing visual direction, information density, workspace hierarchy, and overall appearance unless a change is necessary to make the system more consistent or reusable.

The priorities for this pass are:

**architecture → primitives → components → variants → variables → composition → responsive behavior → interaction states → naming → developer handoff**

Do not merely create additional screenshots.

Build the underlying system.

# 70. COMPONENT BOUNDARIES

Choose component boundaries that correspond to meaningful behavioral responsibilities.

For example:

A **Tab** should be a reusable component.

A tab's 2-pixel underline should **not** be a standalone product component.

A **Tree Item** should be reusable.

Every individual indentation wrapper should not become an unrelated component.

A **Sidebar** should be a compound component.

The entire application should not be one monolithic component.

Balance reuse with comprehensibility.

---

# 71. DO NOT OVER-COMPONENTIZE

Avoid turning every frame, label, divider, or tiny grouping into a public component.

Componentize something when it has one or more of these characteristics:

- reused
- stateful
- configurable
- semantically meaningful
- behaviorally meaningful
- independently maintained
- important to consistency

Use ordinary frames and Auto Layout internally where a separate reusable component adds no value.

---

# 72. REDUCE DUPLICATION

Audit the generated design for near-duplicate patterns.

Examples:

If three sections contain slightly different icon buttons, consolidate them.

If navigation rows differ only in icon and label, reuse one component.

If multiple menus use identical rows, reuse Menu Item.

If several metadata fields have the same structure, use Property Row.

If all docked panels share the same header architecture, use common panel primitives.

Prefer composition over duplication.

---

# 75. QUALITY BAR

The final file should no longer merely answer:

> “What should this application look like?”

It should also answer:

> “What are the fundamental UI primitives?”

> “Which pieces are reusable components?”

> “Which components compose other components?”

> “What state variants exist?”

> “How does resizing work?”

> “How do panes split?”

> “How are navigation systems related?”

> “How does the layout respond when panels disappear?”

> “Which design tokens control the system?”

> “How would a frontend engineer implement this?”

> “How can hundreds of future screens remain consistent with this architecture?”

The result should feel like the beginning of a **real application platform design system**, not a design exercise.

Think of this pass as converting the original visual prototype into the equivalent of a mature professional UI framework for a browser-based workstation.

Preserve the strengths of the existing visual design while making the underlying architecture:

**systematic, composable, reusable, scalable, state-aware, responsive, implementation-friendly, and maintainable.**
