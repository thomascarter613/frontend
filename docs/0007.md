Using the professional workspace shell, production design system, interaction architecture, product-surface taxonomy, canonical resource/object model, end-to-end workflow architecture, and collaboration/governance architecture already established, now perform an **Extensibility, Customization, Integrations, Custom Resource Types, and Platform Configuration Architecture pass**.

Do **not** redesign the application shell.

Do **not** create a second design system for extensions.

Do **not** create isolated mini-applications that merely appear inside iframes or disconnected dashboards.

Do **not** allow extensions to bypass the canonical Resource, View, Workflow, Permission, Policy, Activity, Audit, Command, Inspector, and Workspace models already established.

Do **not** treat customization as arbitrary visual theming.

Do **not** expose implementation-level APIs, manifests, or developer terminology to ordinary users unless they are inside an explicitly advanced/developer-oriented surface.

Instead, define how the platform can be **adapted, configured, extended, connected, and specialized** while remaining one coherent professional workstation.

The first seven passes established:

1. the persistent workspace shell and visual architecture
2. the production component/design system
3. the interaction and workspace behavior model
4. the product modules, surfaces, and view archetypes
5. the canonical resource/object model and information architecture
6. the end-to-end workflow and task architecture
7. the collaboration, permissions, governance, security, and administration architecture

This eighth pass must answer:

> **How can users, administrators, designers, and developers safely adapt the workstation to new domains, data models, workflows, tools, integrations, and specialized experiences without breaking the core product architecture?**

The goal is to transform the product from:

```text
A sophisticated fixed application
```

into:

```text
A coherent extensible application platform
```

while preserving:

```text
shared resources
shared navigation
shared commands
shared design system
shared workspace behavior
shared permissions
shared lifecycle rules
shared search
shared activity
shared governance
```

The priorities for this pass are:

**configuration → schema → custom resource types → custom properties → custom views → forms → templates → workflow configuration → commands → actions → integrations → extensions → contribution points → discoverability → installation → permissions → lifecycle → compatibility → diagnostics → developer handoff**

# 8. DEFINE CANONICAL TERMINOLOGY

Use these terms consistently.

## Configuration

A user- or administrator-defined setting that changes platform behavior without introducing arbitrary code.

## Custom Resource Type

A workspace-defined Resource schema built on the canonical Resource model.

## Field

A structured property definition associated with a Resource Type or Collection.

## View Definition

A persistent configuration describing how resources are represented.

## Template

Reusable starting content/configuration for creating Resources.

## Action

A user-invokable operation performed against Resource context.

## Command

An invokable application operation discoverable through the Command Palette and potentially menus/shortcuts.

## Integration

A connection between the platform and an external service, system, or data source.

## Extension

An installable capability package that contributes features through defined platform extension points.

## Contribution Point

A specific platform location or capability to which an Extension may add behavior.

## Connector

A specialized Integration for exchanging data or actions with an external system.

## Provider

An Extension or Integration that supplies a particular capability.

```text
Core App
+
a collection of foreign plugins
+
separate admin builders
+
unrelated external dashboards
+
random custom pages
```

Instead, its architecture should remain:

```text
ONE PLATFORM KERNEL

supporting

CONFIGURATION
+
CUSTOM RESOURCE TYPES
+
CUSTOM VIEWS
+
FORMS
+
TEMPLATES
+
ACTIONS
+
WORKSPACE APPS
+
INTEGRATIONS
+
EXTENSIONS

through

DEFINED CONTRIBUTION POINTS
```

Every new capability should still participate in:

```text
Workspace
Resource Identity
Search
Commands
Views
Permissions
Activity
Audit
Design System
Lifecycle
Error Recovery
```

```text
CORE PLATFORM
      │
      ▼
CONFIGURATION
      │
      ├── Resource Types
      ├── Fields
      ├── Views
      ├── Forms
      ├── Templates
      ├── Actions
      └── Modules
      │
      ▼
WORKSPACE APPS
      │
      ▼
EXTENSIONS / INTEGRATIONS
      │
      ├── Commands
      ├── Editors
      ├── Panels
      ├── Inspectors
      ├── Workflow Steps
      ├── Search
      ├── Data Providers
      └── External Actions
      │
      ▼
SAME PROFESSIONAL WORKSPACE
```

The user's mental model should remain:

> **“I am extending my workspace.”**

not:

> **“I am assembling several unrelated applications.”**
